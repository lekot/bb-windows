# Рабочие копии Git, подготовка и удаление окружений

Тред можно запустить в существующем checkout проекта или в отдельном управляемом **worktree** — рабочей копии с собственной веткой и общими Git-объектами. Это позволяет вести несколько задач параллельно.

На нативной Windows используйте копирование через `.worktreeinclude` и отдельно установленные зависимости. **Bash-хуки `.bb-env-setup.sh` и `.bb-env-teardown.sh` требуют POSIX-среды и на нативной Windows не поддерживаются.** Проверка пяти маршрутов провайдеров в Windows выполнялась в существующем checkout; она не заменяет полную проверку управляемых worktree.

## Управляемый worktree

Встроенный плагин **Worktree** создаёт рабочую копию через `git worktree add` на отдельной ветке. Каталог находится под:

```text
<BB_DATA_DIR>/plugins/environment-git-worktree/host-data/worktrees/<thread-id>/<repo-name>
```

Worktree использует Git-состояние исходного репозитория, поэтому полного клонирования не требуется. Плагин включён по умолчанию. Отключение в **Settings → Installed plugins** сохраняет существующие worktree, но треды, которым требуется новый worktree, ждут повторного запуска плагина.

## Создание треда

В окне создания треда выберите окружение **Worktree**. Из CLI, подключённого к нужному экземпляру:

```powershell
bb thread spawn --project <project-id> --new-environment worktree --prompt "Выполни задачу в отдельной рабочей копии"
```

Замените `<project-id>` идентификатором проекта. Без `--base-branch` bb выбирает базу автоматически. Явное значение точное: `main` означает локальную ветку, `origin/main` — удалённую.

## Копирование локальных файлов

В новой копии появляются только отслеживаемые Git-файлы. Для нужных неотслеживаемых файлов добавьте в корень репозитория `.worktreeinclude` с шаблонами в синтаксисе gitignore:

```gitignore
local-settings.json
fixtures-local/
```

Одна строка задаёт один шаблон; `!` исключает совпадение с предыдущим шаблоном. В Git попадает только список путей, а не содержимое копируемых файлов. Не включайте личные файлы в распространяемый пример или репозиторий.

Копирование выполняется после создания worktree и до запуска setup-хука:

- Каждая рабочая копия получает собственные файлы; символьные ссылки не создаются.
- Существующие файлы, включая отслеживаемые Git, не перезаписываются; пропуск фиксируется в журнале подготовки.
- Символьные ссылки источника пропускаются, запись через ссылку назначения запрещена.
- Несовпавший шаблон, недоступный файл или ошибка копирования отражаются в журнале; подготовка продолжается.
- Каталоги вроде `node_modules` копируются пофайлово и медленно. Зависимости лучше устанавливать отдельно; в POSIX-среде это можно делать setup-хуком.

## Подготовка через .bb-env-setup.sh

Это описание контракта для macOS, Linux и WSL2. На нативной Windows bb сообщает, что POSIX shell-скрипты не поддерживаются.

Если провайдер окружения создал принадлежащий ему путь (`ownsPath: true`), ядро bb запускает найденный в корне `.bb-env-setup.sh` до передачи треда агенту. При подключении существующего checkout или личного workspace (`ownsPath: false`) оба хука не запускаются. Подготовка провайдера, включая `.worktreeinclude`, завершается до setup.

Пример для POSIX:

```bash
#!/usr/bin/env bash
set -euo pipefail
pnpm install
```

Хук выполняется через `env bash` в каталоге нового окружения. Стандартный ввод закрыт; stdout и stderr видны в журнале подготовки треда. Ненулевой код завершения, сигнал или тайм-аут 15 минут прерывают подготовку: агент не запускается.

## Автоматическое удаление

Удаление последнего треда, использующего worktree, запускает очистку сразу. Архивация последнего треда даёт пять минут: если вернуть тред из архива за это время, рабочая копия сохраняется.

Очистка сначала вызывает teardown-хук, затем завершает процессы рабочего каталога и выполняет `git worktree remove --force`. В POSIX-среде процессы получают `SIGTERM`, затем после короткого ожидания — `SIGKILL`. Ветка остаётся, но **незакоммиченные изменения удаляются вместе с каталогом**.

Перед удалением сохраните нужную работу коммитом и перенесите свои терминалы из worktree. Закройте редакторы и процессы, удерживающие файлы: блокировки особенно важны на Windows. Успешный тест восстановления основного Windows-экземпляра сам по себе не проверяет все сценарии очистки worktree.

## Освобождение ресурсов через .bb-env-teardown.sh

В POSIX-среде добавьте `.bb-env-teardown.sh` в корень проекта, если нужно освободить ресурсы вне рабочей копии: например, отдельный тестовый контейнер или резервирование порта.

Хук запускается перед удалением принадлежащего провайдеру пути, включая очистку после неудачного setup. Подключённые пользовательские пути не запускают хук.

`env bash .bb-env-teardown.sh` выполняется в рабочей копии, пока её файлы доступны. Стандартный ввод закрыт; вывод записывается в журналы жизненного цикла сервера. Хук получает такое же очищенное окружение, как setup, и собственный тайм-аут 15 минут. Ошибка фиксируется, но не отменяет удаление worktree.

Идентификатор операции и состояния запуска/завершения сохраняются для каждой попытки. После перезапуска сервер сверяет исходную операцию daemon, а не запускает setup заново. При разрыве RPC очистка отменяет операцию и ждёт завершения её группы процессов. Если daemon недоступен, очистка остаётся ожидающей повторной попытки. Сохранённая отмена предотвращает поздний запуск ещё не начатой операции.

## Диагностика

1. При ошибке создания откройте журнал подготовки треда: там виден ответ `git worktree add`, например неверная базовая ветка или занятое имя.
2. Для POSIX-хука убедитесь, что он закоммичен в исходную ветку. Файл только в локальном checkout не появится в новой копии автоматически.
3. Уберите интерактивные запросы из хуков: stdin закрыт, ожидание ввода заканчивается тайм-аутом.
4. В POSIX-среде проверьте setup вручную в отдельной чистой копии. Teardown проверяйте только на тестовых ресурсах; повторный запуск не должен удалять общие ресурсы.
5. На Windows используйте окружение без Bash-хуков и подготовьте зависимости отдельно.

## Свежие клоны на машинах

Если провайдер клонирует проект на новую машину и владеет этим путём, ядро применяет ту же политику setup/teardown с указанными ограничениями платформ. Пользовательский checkout, подключённый к bb, остаётся неуправляемым и не запускает хуки.

На новой машине нет исходного локального checkout, поэтому `.worktreeinclude` не применяется. Передавайте локальные файлы и секреты через настройки окружения **Machine**, не через Git. Логику кэша и повторного запуска храните в хуке репозитория; рецепт Dockerfile у Modal относится только к сборке образа.

Восстановление файловой системы машины не запускает setup повторно. Запуск треда сам по себе не проверяет отпечаток workspace и авторизацию агента и не устанавливает CLI провайдера.
